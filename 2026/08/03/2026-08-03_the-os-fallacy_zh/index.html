「操作系统谬误」：为什么模型越强，orchestration 反而越重要

Posted on 2026-08-03 Edited on 2026-09-23 In AI Agent
「模型变强，orchestration 层就会消失」，等于说「CPU 变快，操作系统就会消失」。CPU 确实杀死了内存覆盖技术和手工 DMA，但进程管理、权限控制、设备驱动不仅没消失，反而更重要了。orchestration 在三处重新分配了位置，附一条可检验的吸收判别式。

一个我反复遇到的论断

大意是：agentic coding 的工程层（上下文裁剪、编排框架、外部规则）都是为了绕过模型当前缺陷搭的临时脚手架。推理模型一变强、长上下文一变便宜，这些东西就没有存在理由了，所以别在 orchestration 上投入，那是过渡期的拐杖。

这个论断有一半是对的，而且相当锋利。错的那一半，方向没错，错在级别。

它等价于：因为 CPU 越来越快，所以操作系统会消失。

CPU 变快确实杀死了一批 OS 层的东西：内存覆盖（overlay）技术、手工 DMA 管理、为省几个周期写的汇编内循环，当年是核心技艺，今天没人碰。但进程管理、权限控制、设备驱动、文件系统不仅没消失，反而随硬件变强更重要：硬件越强，跑在上面的东西越多，需要隔离、调度、审计的边界就越多。

先把对的那一半说完

这个论断背后有一条原则，我认为它完全成立：

任何依赖中间层抽象来填补底层缺陷的方案，最终都会被底层技术的进步淘汰。

这条原则很好用，已经淘汰了一批东西，下面这张表都有数字：

被淘汰的 被什么替代 证据
CoT prompting 推理模型内置推理 Wharton GAIL：对推理模型用 CoT 只换来 +2.9-3.1% 准确率，代价是 +20-80% 时间
Output parser / retry 循环 Structured Outputs 合规率 35% → 100%
Few-shot 模板机制 零样本能力 部分任务里 few-shot 反而降低性能
基础 tool calling 编排 原生 function calling 已是所有主流 API 的标准参数
视觉 OCR pipeline 多模态原生输入 主流模型直接吃图

如果你 2023 年写的 agent 代码大半是这些，那确实白写了。这条原则的价值在这儿：提前告诉你哪些工作会短命。

错误发生在下一步，把所有 orchestration 都归类成「填补模型缺陷」。

顺手说一个方法论问题：那篇文章引用了一篇不存在的论文

这个论断的第三层依据是：新一代稀疏注意力机制（文中写作 “NSA+”）让模型可以自主管理上下文，外部上下文管理因此没必要了。

我去查了，公开文献里没有 “NSA+” 这个东西。真实发表的是 NSA（2025 年 2 月，arXiv 2502.11089，ACL 2025 最佳论文）和 DSA（DeepSeek Sparse Attention，2025 年 9 月随 V3.2 部署），后续还有一篇叫 NOSA（2025 年 10 月）。

而且 NSA 论文自己写得很清楚，它做的只是计算效率优化，跟语义理解提升是两回事：

可训练的稀疏注意力只能缓解 memory-bound 瓶颈，不能减少 KV cache 大小。

它在稀疏阶段每个 query 只挑约 2048 个 KV 条目，做的只是近似，并不保证模型"读懂"了全部上下文。

反方向的实证也在累积：Chroma 测了 18 个前沿模型，每一个模型在每一个输入长度增量上，输出质量都随 token 增加而下降；标称 200K 窗口的模型约 130K 处已不可靠，“Lost in the Middle” 中段准确率掉 30% 以上，有效上下文与标称上下文的差距最高达 99%。

所以「长上下文会吃掉上下文管理」这个前提本身站不住，支撑它的那条引用还是虚构的。

拎出这段，不只是为了抓错，也因为这类论断现在很容易被 AI 协助生成，生成出来的东西看起来完全像真的：术语对，时间线对，语气的确定性甚至比真论文更强。唯一的防线是回到源头，这也是这篇文章的一个副论点。

那么 orchestration 究竟去哪了：三处重新分配

它没有消失，换了位置，总量还在增加。

一、被 RL 烘进模型权重。Cognition 训练 SWE-1.5、Cursor 推出 Composer 2，都是在真实任务环境里端到端 RL，把 plan-execute 循环、错误恢复、工具选择内化成权重。这是那个论断最有力的间接验证，但路径恰好相反：scaffold 并没有被去掉，它沿着 scaffold → 训练数据 → 模型权重这条路，被模型吃掉了。

二、标准化成协议。MCP 把 N×M 的工具集成问题压成 N+M，SDK 月下载量从 2M 涨到 68M，并入 Linux Foundation。orchestration 没消失，是变成了基础设施，就像 HTTP 之于 web，没人再说"我在做 HTTP 编排"，因为它已经是地基。

三、压薄成 thin harness。Claude Code 的 agent 主循环大约 50 行（while(tool_call) → execute → feed results → repeat），18 个工具，单线程，没有 multi-agent swarm。但它外面包着 29,000+ 行 harness。主循环越来越简单，外围的工程反而越来越多。

一条可检验的判别式

把那 29,000 行拆开，能分成七类，每一类都有一个「为什么模型吸收不了它」的理由：

类别 典型内容 为什么留在 harness
A. 外部世界接口 Bash、文件读写、Git、MCP、IDE 物理鸿沟：模型产文本，不产 syscall
B. 信任边界 权限、审批、沙箱、黑白名单 架构原理：不能让被审计者当审计员
C. 跨会话状态 会话持久化、任务跟踪、项目记忆 时间维度：状态必须活得比任何单次 context 长
D. 多 agent 协调 子 agent 派发、worktree 隔离、消息路由 这是分布式系统问题，与模型能力正交
E. 经济管理 token 预算、prompt caching、模型路由 模型看不到全局成本
F. 人机界面 终端渲染、diff、hooks、slash command 这是 agent 之外的接口，不是推理问题
G. 工程脚手架 schema 校验、工具检索、重试 理论上可吸收，目前不划算

A 到 F 全部涉及模型之外的东西：物理、信任、时间、协调、经济、人。G 是唯一一类会随成本下降被吃掉的。

于是判别式可以写成一句话：

能被压缩成「更好的 next-token-prediction」的能力，会被模型吸收。
涉及模型外部世界（物理 / 信任 / 时间 / 协调 / 经济 / 人机）的能力，会留在 harness。

这条式子正着用反着用都行，反着用更狠：如果你在做的事能被压缩成"更好的提示词模式"，大概率会被下一代模型消灭。拿它查一遍自己的技术押注，比读十篇趋势预测有用。

但 scaffold 到底还重不重要？这是可以证伪的

不用争论，看数字：

  • 同一个模型，换 scaffold，差 12 到 30 分：SWE-bench Pro 上基础与优化 scaffold 之间有 22 分以上的摆动，单是把上下文检索做好就能加 4 到 10 分。
  • Epoch AI 的结论：一个优秀的模型配平庸的 scaffold，会输给一个良好的模型配出色的 scaffold。
  • SWE-bench Verified 上榜首已经 85% 到 94%，但更接近真实场景的 SWE-bench Pro，最高分只有约 23%。

最后这组对比值得停一下：同一批模型，换一套更像真实工作的题，分数掉到四分之一。掉下去的那部分，缺口在"世界没有被组织好"，跟模型智能关系不大，这正是 harness 要干的活。Anthropic 工程博客说得最准：

agentic 系统的主要短板不是模型的智能，而是为它组装出的那个世界的质量。

顺带说，"简单胜于复杂"确实有权威背书，Anthropic 官方指南说最成功的实现都没用复杂框架，用的是简单可组合的模式。但「简单」和「不存在」是两件事：Claude Code 那 50 行循环能简单，正因为下面压着 29,000 行。

两条我因此改掉的判断

第一条：易用性是一种由底层工程师偿还的债。

上层抽象越简单，底层必然越复杂，这两者是反向耦合的。SQL 一行查询背后是博士级难度的查询优化器；pip install 背后是 HTTP/2 + TLS + DNS + TCP + IP 整条栈；git push 背后是分布式一致性与冲突检测；iPhone 的 “It Just Works” 背后是 iOS 加 Secure Enclave 加几千人的工程团队。

机制有四条：用户越多需求维度越杂；每加一层抽象就多一组排查空间；上层接口一旦稳定就不能动，底层变化都得伪装成"接口没变"；越基础的东西挂掉越是灾难，可靠性 bar 只会单调上升。

反直觉的结论：软件"用起来很简单"，问题未必简单，往往是有人替你把复杂度承担了。

第二条：便宜是滞后指标，难是领先指标。

CRUD 今天极其便宜，不代表问题本身简单，是四十年的基础设施投资被压缩进了一个 pip install，你消费的是被凝结的复杂度化石燃料。

阶段 难度 时代
前沿 博士论文级 Codd 的关系代数，1970s
框架 专家领域 SQL 标准化，1980s
标准 多数人可用 MySQL / Postgres，1990s
基础设施 不可见 Rails / Django，2000s
商品化 小时级搭完 2020s 的 CRUD

Harness 今天很难，意味着它正处在这张表的第一行：今天的 hard，就是 2040 年的 pip install。

所以：押注 cheap 的东西是消费过去的复杂度，边际价值递减；押注 hard 的东西是生产未来的复杂度，边际价值递增但波动大。

落到 SRE 视角

我做的是基础设施可靠性，这件事在我这儿有个更直接的说法。

接口问题不会因为任何一侧变强而消失。工具集成、安全门禁、系统边界管理、跨会话错误恢复，管的都是模型与外部世界之间那道界面，不只是在填补模型当下的缺陷。模型变强只会让界面另一侧动作更有力、后果更大，界面本身也就更需要被设计。

这正是操作系统的历史：CPU 变快没有让 OS 消失，只让"谁能碰哪块内存、哪个进程能发哪个 syscall、失败时谁来回滚"变得更要紧。

agent harness 走的是同一条路，而且比 OS 那次更急，因为 CPU 不会自信地编造一个不存在的答案，模型会。
