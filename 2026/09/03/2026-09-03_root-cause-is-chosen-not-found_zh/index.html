复盘时争「哪个才是根因」，为什么总争不出结果

Posted on 2026-09-03 Edited on 2026-09-23 In SRE 方法论
拿一次 Kafka 积压的复盘举例：把根因写成一条因果链，每条边做反事实检验，再列出没解释掉的观察。链画出来之后，争论就变成了比较在哪一刀切最划算。

前段时间处理过一次 Kafka 消费积压。告警是多个租户的 consumer lag 一路上涨，查到最后，问题出在 ClickHouse 的系统表里（完整复盘）。写复盘时出现了两种说法：一种说根因是 CH 升级留下的旧表，一种说是服务器内存上限给得太低。两种都有道理，谁也说服不了谁。

后来我想明白了，这个争论本身问错了。根因并不是事故里某个客观存在的点，它是我们在一条因果链上挑出来下刀的位置。挑哪里，看哪一刀最便宜、最可靠。

把链画出来

「根因是 X」这种句式会逼着人把一条链压成一个词。那次事故的链是这样的：

flowchart TB A["CH 升级留下带数字后缀的旧系统日志表"] --> B["僵尸表体积累积到 TiB 级"] B --> C["后台 merge 挑到僵尸表的 parts"] M["merge 调度被触发"] --> C C --> D["内存一秒内从 2 GiB 冲到 21.6 GiB 上限"] L["服务器内存上限 21.6 GiB"] --> D D --> E["并发插入被 Code 241 杀掉"] E --> F["失败批次进入 30s sleep 加 rebalance 重试循环"] F --> G["多租户 consumer lag 单调上涨（可见告警）"]

链上有七个节点，每个都可以是切断点。「升级残留」和「内存上限太低」两种说法并不冲突，只是下刀的位置不同。

在哪一刀切

同一条链上，各个切断点的代价、可靠性和周期差别很大：

切断点 动作 代价 可靠性 撤回成本
升级不留残留 改升级流程，升级后审计并清理 高，跨团队，周期长 高，从源头断 撤回免费
僵尸表不长大 给内部日志表加 TTL，关掉最大的几张 低，配置层 高 撤回免费
merge 不引爆 限制单次 merge 的内存与并发 中 中，只是降低概率 撤回免费
抬高内存上限 改服务器内存上限 最低 低，只是推后 撤回免费
消费者不死循环 改重试策略 中 低，治的是症状 一次中断

团队常常想修最深的那个原因，可最深的往往最贵、周期最长，还得等别的团队配合。链画出来以后，讨论就从站哪边变成了算哪边便宜。那次最后落地的是配置层：给内部日志表加 TTL、给 merge 封内存上限，另外在升级 runbook 末尾加了一步残留审计。

反事实检验

时间上先发生的事，不一定是原因。要把因果边和伴随现象分开，只需要问一个问题：如果上游节点没发生，下游还会发生吗？

回答 含义 处理
不会 上游是下游的必要条件 进主链
还会 上游是伴随现象 移出主链，留在时间线里
不知道 无法判定 标为未验证，不得进入主链

拿那条链跑一遍，砍掉了一条边。

报错里有一行 current RSS: 8.85 GiB，我第一反应是内存慢性泄漏：RSS 长期偏高，一次 merge 就撑爆了。换成反事实的问法再看：假如 RSS 一直待在 2 GiB 的基线，那次 merge 还会把并发插入杀掉吗？会。内存是在一秒内冲到 21.6 GiB 上限的，基线高一点低一点改变不了结果。所以 RSS 偏高只能写进时间线，主链里没有它的位置。

很多复盘写下来的是时间上先发生的事，没人问过这些事在因果上是不是必要的。这一步最容易被跳过，跳过的后果是修完之后事故照样复发，因为修掉的是伴随现象。

能做实验就做实验，去掉一个条件再压一次；做不了实验只能推理，但要标成「未验证」。一份 RCA 里有几条未验证的边，基本就能看出它有多可靠。

必要条件和充分条件

一条边通过反事实检验，只能说明上游是必要条件，说明不了它充分。

僵尸表存在，单靠它不会 OOM，还需要 merge 调度正好挑到它，内存上限也正好在那个量级。三个条件要同时满足。链图里从旁边并进来的 merge 调度被触发 和 服务器内存上限，就是另外两个必要条件。

几个条件必须同时满足时，打断任意一个，事故就不会发生。所以防复发的动作应该落在最便宜的那个必要条件上，最「根本」的那个未必划算。前面那张表里配置层 TTL 性价比最高，原因就在这里：它打断的是「僵尸表涨到 TiB 级」，阻断效果和改升级流程一样，成本低一个数量级。

没解释掉的那几条观察

人写的复盘里很少有这一节，但它最能防住伪根因。

做法是把这次收集到的观察逐条过一遍，看当前的解释能不能覆盖，覆盖不了的列出来。这一步要读懂每条观察在说什么，再判断解释有没有涵盖它，做不成数值比较，所以应该留给能读语义的那一层，不适合写成一条规则。如果有三条观察解释不了，这个根因多半不完整。

放到那次事故上，至少能问出两个问题。为什么是这几个租户先出现 lag，其他租户没有？merge 挑到僵尸表是随机的还是有触发条件，如果是随机的，之前几个月为什么一直没出事？这些问题的答案不影响这次修复是否正确，但决定了这个解释完不完整，也决定了几个月后同一条链会不会换个样子再来一次。

这件事 agent 比人容易做好。人会不自觉地略过不符合自己判断的观察，跟能力无关；agent 会把每一条证据都老老实实过一遍。在 RCA 上，我觉得这是 agent 比人强的少数几个地方之一。

agent 也有自己的坑：它不知道自己漏查了什么。如果只查了三个维度，覆盖率 100% 说明不了任何问题。所以报覆盖率时，要一起报查了哪些维度、没查哪些，只报一个百分比会显得比实际好看。

RCA 和 triage 反着来

同一套假设管理机制，放在 triage 和 RCA 里，用法正好相反。

triage 跟时间赛跑，止住就算成功，可以不知道根因。它最常见的失败是收敛太早，看到一条变更记录就锁定了，所以门禁要防止拖太久：连续几条假设被否掉，就强制升级。RCA 要的是正确，最常见的失败是把相关当成因果，所以门禁要防止停太早：必须做反事实，必须列残余，次强的解释要留到最后。

两者手里的证据也不一样。triage 时数据还在线上，做 RCA 时数据可能已经被 retention 删掉了。结论的去向也不同，triage 的结论决定下一个动作，RCA 的结论决定架构上往哪投钱。triage 判断错了，多花十分钟；RCA 判断错了，团队可能花一个季度修错地方，事故还会再来。RCA 值得付更高的严格度成本，就是因为这个。

次强的解释要写清楚为什么被排除。读复盘的人需要知道你考虑过什么，不然他会在会上把你已经排除掉的那个再提一遍。

证据要在事中留下

做 RCA 最实际的困难，往往是证据已经没了：指标过了 retention，日志滚掉了，pod 被重建，临时表被清理。等到坐下来复盘，反事实检验要用的数据经常已经拿不到。那次事故能查清楚，靠的是引擎内部 1 秒粒度的 metric log，而这份数据也有自己的保留期。

所以 RCA 要往前挪到 triage 阶段：事中就把关键查询的原始返回落盘，别只把结论写进报告。

这件事成本很低，写文件而已，收益要几天后才看得到。不做也不会马上出问题的事，靠自觉一定会漏，得写成硬要求。在我的 oncall harness 里它是一条验收标准：每次调查建工作目录时顺手建一个 evidence/，每次查询的原始返回按查询和时间窗命名存进去。

目前这套设计我只实装了 triage 那一半，也就是止损的部分。RCA 这一档还靠事后手写案例，因果链、反事实三态、覆盖率门禁都还是设计，没有代码。

反事实检验也有做不到的地方。分布式系统里很多边没法做实验，总不能为了验证一条边，在生产上再造一次事故。这时候反事实只能靠推理，文档里就必须看得出哪条是推理、哪条有证据，「未验证」这个状态就是为此设的。
